# fastik benchmark: NeuroMechFly vs. flygym.ik

Correctness cross-check and throughput/latency benchmark for fastik, using
the NeuroMechFly leg body plan and real recorded fly kinematics, against
[flygym.ik](https://github.com/NeLy-EPFL/flygym)'s MuJoCo-based solver.
Covers the Rust API (`src/`, `cargo run`), the Python bindings
(`scripts/bench_python.py`), and the C++ bindings (`cpp/bench_cpp.cpp`).

## Layout

- `assets/neuromechfly_ypr_legs.json`: the kinematic tree, exported from
  flygym via `../../flygym/scripts/export_model_for_flyik.py`. 31 joints (a
  free-floating "thorax" root plus, per leg, `thorax_coxa` (3 dof),
  `coxa_trochanterfemur` (2 dof), `trochanterfemur_tibia` (1 dof),
  `tibia_tarsus` (1 dof), and a fixed `claw` node), 42 dofs total.
- `assets/fixtures.json`: sample frames generated by
  `scripts/generate_fixtures.py`, of three kinds:
  - **synthetic**: keypoint targets generated by running this exact model's
    own forward kinematics (MuJoCo) on *real* recorded ground-truth joint
    angles -- exactly reachable by construction, so the solver has no excuse
    not to recover them. `synthetic_frames[0]`'s target also doubles as the
    fixed target for the single-frame-latency benchmark, across all three
    bindings.
  - **real**: real (noisy) mocap keypoints from a recorded fly (flygym_demo's
    bundled Spotlight clip), rigidly (Kabsch) aligned into this model's own
    frame convention, plus flygym.ik's own solved reconstruction on the same
    targets, for a cross-solver comparison. Sparsely sampled (every 30th
    recorded frame, ~91ms apart) for a diverse spread of poses -- correctness
    only, not used for any performance number.
  - **native rate**: a *contiguous* run of 300 consecutive recorded frames,
    no gaps -- for benchmarking sequence throughput under the frame-to-frame
    motion continuous tracking would actually see (tiled to whatever length a
    given benchmark needs). Performance-only, no flygym.ik reconstruction.
- `src/`: the Rust benchmark binary (`fastik-benchmark`).
- `scripts/bench_python.py`: the same correctness/performance checks against
  fastik's Python bindings instead of the Rust API, for direct comparison.
- `cpp/bench_cpp.cpp` (built via `../cpp/CMakeLists.txt`, target
  `fastik_cpp_benchmark`): the same checks again, against fastik's C++
  bindings. `cpp/json.hpp` and `cpp/forward_kinematics.hpp` are this
  executable's own dependency-free JSON reader and from-JSON forward-
  kinematics replica (mirroring `bench_python.py`'s, since FK isn't exposed
  to C++ either -- see those files' docs).

## Regenerating the fixtures

Requires flygym's own venv (mujoco, scipy, flygym, flygym_demo):

```sh
cd /path/to/flygym && source .venv/bin/activate
python /path/to/fastik/benchmark/scripts/generate_fixtures.py
```

This re-runs `export_model_for_flyik.py` (so the body plan always matches
the fixtures it was generated with) and overwrites both files under
`assets/`.

## Running

```sh
cargo run --release -p fastik-benchmark
```

This reports single-frame latency, single-thread sequence throughput, and
multi-thread sequence throughput (using every core available to the
process), plus one weak-scaling data point sized to however many threads
are currently available. To sweep the weak-scaling test across specific
thread counts, run the same binary repeatedly under `taskset -c`, which
constrains the CPU affinity mask that `std::thread::available_parallelism`
reads:

```sh
for cpus in 0 0-1 0-3 0-7 0-15; do
    taskset -c "$cpus" cargo run --release -p fastik-benchmark | tail -1
done
```

### Python bindings

Requires fastik's Python extension built for the interpreter you run this
with (see the top-level README's "Python" install section) and flygym's own
venv (for the flygym.ik cross-check):

```sh
cd /path/to/flygym && source .venv/bin/activate
python /path/to/fastik/benchmark/scripts/bench_python.py
```

It reuses the exact same `assets/fixtures.json` as the Rust benchmark, so
the two are directly comparable. One thing it can't do that the Rust one
can, since it's not exposed to the Python bindings: forward kinematics on
its own -- see the script's docstring for the independent from-JSON
reimplementation used instead.

### C++ bindings

Builds via the same CMake project as the C++ bindings' own test suite (see
the top-level README's "C++" section):

```sh
cmake -S ../cpp -B ../cpp/build -DCMAKE_BUILD_TYPE=Release
cmake --build ../cpp/build -j
../cpp/build/fastik_cpp_benchmark
```

Same fixtures, same methodology (per-frame-then-aggregate stats, flattened
`Missing` + `Position3D` observations) as the Rust and Python benchmarks, so
all three are directly comparable.

## Results (this machine: Intel i9-11900K, 8 physical cores / 16 logical threads via SMT)

### Correctness

Synthetic exact-fit frames (default config, `neutral_pose_weight=1e-3`):
keypoint fit residual rms ~0.0015-0.003 (model units), max angle error vs.
ground truth 1.4-3.9 deg. With `neutral_pose_weight=0`, angle error drops to
~0.00001-0.00008 deg (float32 noise floor) -- confirming the residual error
at default settings is entirely the intentional neutral-pose regularization
trading off against an already-tiny residual, not a solver or forward-
kinematics bug.

Real mocap frames, warm-started in sequence, cross-checked against
flygym.ik on the same (Kabsch-aligned) targets: fastik's own fit residual
rms=0.076, cross-solver agreement with flygym.ik rms=0.084 -- consistent
with the residual scale expected from real anatomical differences between
this individual fly and the generic template model.

Both numbers are identical (to 5 decimal places) across the Rust API and
the Python and C++ bindings, as expected -- all three call into the same
compiled Rust solver, cross-checked in each case by an independent from-JSON
forward-kinematics replica that doesn't call into fastik at all.

### Performance

Same fixtures and default `SolverConfig` (early stopping via
`position_tolerance`/`angle_tolerance` enabled -- `n_iterations` is a
ceiling, not a fixed cost) across all three bindings:

| metric | Rust | Python | C++ |
|---|---|---|---|
| single-frame time (latency) | 155 us | 161 us | 159 us |
| single-thread sequence throughput | 215 us/frame (4,650 fps) | 217 us/frame (4,600 fps) | 214 us/frame (4,680 fps) |
| multi-thread sequence throughput (16 threads) | 34,800 fps | 31,000 fps | 32,200 fps |

- **single-frame time**: one `solve()` call from a fresh neutral pose against
  a fixed real target (`synthetic_frames[0]`), no warm start.
- **single-thread sequence throughput**: `SequenceSolver`'s `solve_frame`
  warm-started across the 300-frame native-rate fixture (contiguous, real
  frame-to-frame motion).
- **multi-thread sequence throughput**: `solve_sequence_segmented_parallel`
  on a longer sequence tiled from the native-rate fixture (segment_len=200,
  sized to one segment per available thread), using all 16 logical cores.

All three bindings are at parity within run-to-run noise: Python (PyO3) and
C++ (`cxx`) both call straight into the same compiled Rust solver with no
meaningful marshaling overhead, so there's no separate "binding overhead"
story to tell here.

### Weak scaling (Rust only)

Fixes work per thread at one 200-frame segment and scales total frames with
thread count (`taskset -c` controls how many cores
`solve_sequence_segmented_parallel`/`available_parallelism` see):

| threads | total frames | elapsed | efficiency (vs. 1 thread) |
|---|---|---|---|
| 1  | 200  | 42.4 ms | 1.00 |
| 2  | 380  | 43.4 ms | 0.98 |
| 4  | 740  | 43.9 ms | 0.96 |
| 8  | 1,460 | 45.9 ms | 0.92 |
| 16 | 2,900 | ~87 ms  | ~0.49 |

Near-ideal weak scaling through 8 threads: elapsed time barely grows even as
both thread count and work scale together. At 16 threads, elapsed time
roughly doubles and run-to-run variance grows noticeably (84-109 ms across 5
runs, vs. single-digit-millisecond spread at 1-8 threads) -- this machine
has 8 physical cores with 2 SMT threads each, so 16 threads means using
*both* hardware threads on every physical core; SMT siblings share a core's
execution resources, so the second thread on each core doesn't add a full
core's worth of throughput, and any other activity on the machine competes
more visibly once every logical CPU is in use.
